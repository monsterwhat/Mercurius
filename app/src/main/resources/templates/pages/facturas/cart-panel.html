{! pages/facturas/cart-panel - the POS sale panel fragment (T37). Rendered standalone by GET /api/app/pos/cart-panel AND included by pages/facturas/factura.html — single source of truth for the markup (T18 pattern). It is the hx-target of every POS mutation twin: POST /api/app/pos/scan-form (codigoBarra, cantidad) POST /api/app/pos/item/{codigo}/qty-form (delta) POST /api/app/pos/item/{codigo}/qty-set-form (cantidad, decimal directo) POST /api/app/pos/item/{codigo}/remove-form POST /api/app/pos/client-select-form (clientCode) POST /api/app/pos/puntos-form (puntosARedimir) POST /api/app/pos/facturar-form (OOB refresh from resultado) POST /api/app/pos/override-authorize-form (OOB refresh on success) POST /api/app/pos/cancel-form Classic POS closing order lives here (it cannot move to factura-body.html: every mutation above re-renders this fragment, so totals and actions must be re-rendered with it or they would go stale): Descuento -> IVA -> TOTAL (plus the puntos row), then Cancelar before Facturar. The rows table scrolls inside its own viewport; the totals, the payment trigger and the two closing actions sit OUTSIDE it, so a long sale can never push "Facturar" out of reach behind a scrollbar. Model ("panel" bound key, Map): items List - {codigo,nombre,cantidad,precioEfectivo,totalLinea,promo,precioPersonalizado} vacio bool totalCarrito / totalDescuento / totalImpuesto / descuentoPuntos totalPagado / vuelto / vueltoString hasOverrides bool - any row carries precioPersonalizado authorizedBy String|null - supervisor on the session clienteCode / clienteName / clientePuntos mensaje Map|null - {status,severity,summary,detail} Every number comes from CarritoService (server-computed); this template performs no math. Quantity +/- and remove are per-row micro-forms so HTMX posts stay plain urlencoded (no hx-vals JSON, keeping Qute braces out). !}
